# Constraint 0030

## Title
Java programming language rules and standards

## Description
This set of constraints defines the state-of-the-art rules and architectural standards for Java development within Omniwrench.

### 1. Robustness, Input Defenses & Null Safety
- [CS-0030.1] **Mandatory Precondition Defenses**: Every constructor, public method, and protected method shall start with explicit boundary and parameter validation checks.
  - [CS-0030.1.1] **Null Rejection**: Object parameters shall be validated using `java.util.Objects.requireNonNull` with a descriptive error message immediately upon entry.
  - [CS-0030.1.2] **Range and Boundary Bounds**: Numerical limits, array lengths, buffer indices, and timeout limits shall be explicitly validated against valid domain ranges. Invalid parameters shall immediately trigger an `IllegalArgumentException` or `IndexOutOfBoundsException` before any state mutation occurs.
- [CS-0030.2] **Absolute Null Safety in Domain Logic**: The passing or returning of `null` values across module or architectural boundaries is strictly prohibited. Collections and arrays shall never contain `null` elements. Methods that return collections or arrays shall return empty instances (`Collections.emptyList()`, `Collections.emptyMap()`, zero-length arrays) or `java.util.Optional<T>` rather than `null`.
- [CS-0030.3] **Defensive Copying at Boundaries**: Mutable objects passed into constructors/methods or returned from accessors must be defensively copied (`List.copyOf()`, `Map.copyOf()`) to preserve encapsulation.

### 2. Object-Oriented Design & Bounded Resource Execution
- [CS-0030.4] **Bounded Object Instantiation & Pools**: Continuous execution paths shall enforce a bounded object allocation model. Unbounded instantiation in high-frequency loops is forbidden.
- [CS-0030.5] **Bounded Threading Execution Models**: The manual instantiation of unmanaged threads (`new Thread().start()`) or unbounded thread pools (`Executors.newCachedThreadPool()`) is strictly prohibited. All concurrent tasks shall execute within globally bounded, explicitly sized thread pools configured with dedicated work queues and explicit rejection handlers (`RejectedExecutionHandler`).
- [CS-0030.6] **Object-Oriented Behavioral Patterns**: Core domain logic shall leverage expressive Object-Oriented patterns:
  - [CS-0030.6.1] **State Pattern**: Agent reasoning cycles and protocol handshakes must be modeled using the State pattern.
  - [CS-0030.6.2] **Strategy Pattern**: Interchangeable algorithms (tokenizers, tool dispatchers, scoring algorithms) shall be encapsulated via the Strategy pattern.
  - [CS-0030.6.3] **Factory Pattern**: Complex object instantiation shall be governed by Static Factory Methods or dedicated Factory classes.
- [CS-0030.7] **Strong Immutability & Encapsulation**: Classes shall enforce uncompromised encapsulation. All fields must be `private` and, whenever possible, declared `final`.

### 3. Exhaustive Exception Processing & Lifecycle Management
- [CS-0030.8] **Exhaustive Exception Coverage**: All execution paths must be fully protected against runtime failures. Absolutely no exception shall be left unhandled or allowed to silently crash a thread.
  - [CS-0030.8.1] **Boundary Interception**: Every asynchronous entry point, background runner, REST controller, or WebSocket listener must wrap its core logic in comprehensive `try-catch` blocks.
  - [CS-0030.8.2] **Domain Exception Translation**: Low-level operational exceptions (`IOException`, `InterruptedException`) shall be caught and translated into expressive domain unchecked exceptions.
- [CS-0030.9] **Mandatory `try-with-resources`**: Any resource implementing `java.lang.AutoCloseable` or `java.io.Closeable` must be strictly managed using a `try-with-resources` statement.

### 4. Core Java Typing & Application Architecture
- [CS-0030.10] **Strong and Explicit Typing Mandate**: Local variable type inference (`var`) is strictly forbidden. Every variable, field, parameter, and return type shall be explicitly declared with its concrete or interface type to ensure absolute static typing clarity.
- [CS-0030.11] **Semantic POJOs & Equality Contracts**: Data carriers shall be implemented as standard Java classes. Every data carrier class shall implement robust, explicit `equals` and `hashCode` methods using `Objects.equals`/`Objects.hash`.
- [CS-0030.12] **Sealed Hierarchies for Exhaustive Modeling**: Bounded domain models and event hierarchies shall utilize `sealed` interfaces or classes.
- [CS-0030.13] **Constructor Dependency Injection**: Spring Boot component wiring shall strictly use explicit constructor injection. Field injection via `@Autowired` is prohibited.
- [CS-0030.14] **GraalVM Native Image Reachability**: Application code must maintain structural compatibility with GraalVM Native Image ahead-of-time compilation.

### 5. Clean Code Traceability & Verification Standards
- [CS-0030.15] **Traceability Reference Mandate**: Every class, interface, method, and logically distinct block must include comment annotations referencing the explicit requirement, feature request, task, or bug fix it addresses.
- [CS-0030.16] **Structured Parameterized Logging**: All log statements shall utilize SLF4J loggers with parameterized placeholders. String concatenation within log statements is forbidden.
- [CS-0030.17] **Standardized Verification Stack**: Unit and integration testing shall utilize JUnit 5, AssertJ fluent assertions, and Mockito. External transport components shall be verified using Testcontainers.

## Verification
Automated Maven Checkstyle, PMD, and Surefire gates enforcing CS-0030 compliance on every build.
